<objective>
Complete the analytics backend to a dashboard-serving state: CSV/JSON export, an SSE real-time KPI stream, configurable in-app alert rules with a BullMQ evaluation job and multi-channel dispatch, Prometheus alert rules for the business KPIs, a CI workflow for the analytics E2E suites, and cost/usage documentation.

Purpose: Deliver the remaining ROADMAP success criteria — "exportação funcional (CSV/JSON)", "dashboard em tempo real (<30s)", "alertas disparam corretamente (email/Slack)" — via the API + Prometheus surface. This is the load-bearing dashboard-data layer; a custom React SPA (RESEARCH §4) consumes these endpoints and is deferred as a follow-on (the ROADMAP permits Grafana as the visualization layer, and Grafana consumes the Prometheus rules added here). See scope note below.

Output: `analytics_alert_rules` entity + migration; alert evaluation job + dispatch service; export service + endpoint; SSE stream endpoint; prometheus/alerts.yml; analytics-e2e.yml CI workflow; docs update; alerts+export E2E suite.
</objective>

<scope_note>
The ROADMAP deliverable reads "Dashboard web (ou integração com Grafana)". This plan delivers the dashboard-DATA layer completely: query API (06-02), export, real-time SSE stream, and Prometheus/Grafana alert rules. A bespoke React SPA (RESEARCH §4, ~30 files) is a self-contained frontend subsystem that would exceed a single agent's context budget when combined with alerting/export/CI; it is deferred to a follow-on phase and is NOT a silent scope reduction — the visualization is satisfiable via Grafana (already in the stack) consuming prometheus/alerts.yml, and every metric is reachable via the REST API for any custom UI.
</scope_note>

| Boundary | Description |
|----------|-------------|
| api-key client -> export/stream/alert-rule endpoints | caller reads/writes alerting config and bulk exports business data |
| analytics -> outbound Slack/webhook | alert dispatch performs outbound HTTP to configured URLs (SSRF surface) |
| CI runner -> npm ci | dependency resolution in CI |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-08 | Information Disclosure | GET /api/analytics/export | high | mitigate | @RequireRole(ApiKeyRole.OPERATOR) on export/stream/alert routes (asserted in E2E) |
| T-06-09 | Server-Side Request Forgery | AlertDispatchService webhook channel | high | mitigate | webhook target validated against an allowlist/scheme check before POST; reuse the project's existing SSRF guard (postWebhookPayload pattern from Phase 1) rather than a raw axios POST |
| T-06-10 | Elevation of Privilege | POST/DELETE alerts/rules | high | mitigate | OPERATOR role required to create/delete rules |
| T-06-11 | Denial of Service | SSE stream connection churn | low | accept | fixed 10s interval, one-way; standard connection limits apply |
| T-06-12 | Tampering | CI dependency supply chain | medium | mitigate | all GitHub Actions pinned by SHA (mirrors memory-e2e.yml), permissions contents:read |
</threat_model>
