    Migration 012-enable-rls-policies.ts per RESEARCH.md L717-759. Only runs if RLS_ENABLED=true env var set (controlled deployment). Migration logic:

    1. Create tenant_admin role: CREATE ROLE tenant_admin;
    2. For each table (sessions, api_keys, messages, webhooks, automation_rules, analytics_events, intake_leads, knowledge_base_documents, audit_logs):
       - Enable RLS: ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
       - Create tenant isolation policy: CREATE POLICY tenant_isolation_<table> ON <table> FOR ALL USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
       - Create admin bypass policy: CREATE POLICY admin_bypass_<table> ON <table> TO tenant_admin USING (true);
    3. GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO tenant_admin;

    Note: current_setting('app.tenant_id', true) with missing_ok=true prevents error if session variable not set (returns null → policy rejects all rows, safe failure mode).

    Migration down() reverses: DROP POLICY tenant_isolation_<table>, DROP POLICY admin_bypass_<table>, ALTER TABLE <table> DISABLE ROW LEVEL SECURITY, DROP ROLE tenant_admin.

    Run migration conditionally: if (process.env.RLS_ENABLED !== 'true') { console.log('RLS migration skipped (RLS_ENABLED != true)'); return; }. This allows staging to skip RLS while testing application-level scoping.

    Document in RlsConfig: "RLS is defense-in-depth. Application-level scoping (TenantScopedRepository) is primary mechanism. RLS prevents leaks if app code has bugs. Enable in production after validating app-level scoping in staging."

    Create RlsInterceptor implementing NestInterceptor per RESEARCH.md L1058-1073. Inject ClsService and DataSource. In intercept method:

    1. Read tenantId from ClsService: const tenantId = this.cls.get<string>('tenantId'). If missing, skip SET (session variable not set → RLS rejects all rows → safe failure).
    2. Get connection from DataSource pool: const queryRunner = this.dataSource.createQueryRunner(); await queryRunner.connect();
    3. Set session variable: await queryRunner.query(`SET LOCAL app.tenant_id = $1`, [tenantId]). Use SET LOCAL (not SET) so variable resets at end of transaction, preventing connection pool pollution per RESEARCH.md L1050-1073.
    4. Call next.handle() to execute route handler.
    5. In finally block: await queryRunner.release() to return connection to pool.
    6. Use tap(async () => { await queryRunner.query(`RESET app.tenant_id`); }) to clean up session variable after response sent (belt-and-suspenders, SET LOCAL should auto-reset).

    Register RlsInterceptor globally via APP_INTERCEPTOR provider in AppModule. Interceptor runs after guards (tenant context already set by ApiKeyGuard) and before route handlers.

    Configuration: Interceptor only sets session variable if RlsConfig.enableRLS is true (production). In dev/staging, interceptor is no-op (application-level scoping tested without RLS interference).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application code → Database | RLS policies enforce tenant isolation even if app code has bugs (WHERE tenantId missing) |
| Admin queries → Database | Admin can bypass RLS (row_security=OFF) but audit trail records all cross-tenant access |
| Session variable → Connection pool | app.tenant_id must not leak between requests in pooled connections |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-21 | Information Disclosure | Application code forgets WHERE tenantId | critical | mitigate | RLS policies enforce tenant_id = current_setting('app.tenant_id'); query returns empty result if app.tenant_id not set; E2E test proves leak prevention |
| T-09-22 | Information Disclosure | Session variable pool pollution | high | mitigate | Use SET LOCAL (not SET) so variable resets at transaction end; connection pool cannot leak tenantId between requests; E2E test verifies isolation |
| T-09-23 | Repudiation | Admin cross-tenant query not logged | medium | mitigate | audit-cross-tenant.service logs all admin queries with queriedTenantIds, adminUser, timestamp; forensic trail allows operator review |
| T-09-24 | Elevation of Privilege | Non-admin bypasses RLS | critical | mitigate | Admin bypass requires tenant_admin role (DB-level permission); only granted to specific admin users; application cannot grant role (PostgreSQL security) |
| T-09-25 | Denial of Service | RLS performance overhead | medium | accept | RLS adds ~5-10% query overhead (PostgreSQL native, minimal); indexes on tenant_id mitigate impact; acceptable for security benefit |

## Defense-in-Depth Layers

Layer 1: **Application-level scoping** (TenantScopedRepository) — primary mechanism, explicit WHERE tenantId in every query, fast, flexible.

Layer 2: **PostgreSQL RLS** (this plan) — safety net, database-enforced, catches application bugs, production-only.

Layer 3: **Audit trail** — forensic logging, admin cross-tenant access recorded, operator review for abuse detection.

All three layers active in production. Layer 1 alone in dev/staging (RLS disabled for debugging).
</threat_model>
