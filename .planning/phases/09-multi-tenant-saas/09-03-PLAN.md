<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Webhook endpoint → Stripe | Untrusted POST requests must be verified via signature before processing |
| Usage tracking → Billing | Message count must be accurate; under-count = revenue loss, over-count = customer dispute |
| Quota enforcement → Message sending | Bypassing quota enforcement could allow free unlimited usage |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-10 | Spoofing | Stripe webhook | critical | mitigate | stripe.webhooks.constructEvent validates signature using STRIPE_WEBHOOK_SECRET; unsigned requests rejected with 400 |
| T-09-11 | Tampering | Usage count manipulation | high | mitigate | Usage tracking writes directly to DB via UsageService; no client-supplied counts accepted; AnalyticsEvent rows are append-only (no UPDATE/DELETE) |
| T-09-12 | Repudiation | Stripe meter event lost | medium | accept | Stripe meter event emission is fire-and-forget (non-blocking); if emit fails, event logged but message still sent; Stripe has built-in idempotency via identifier; worst case = under-billing (acceptable vs blocking message) |
| T-09-13 | Denial of Service | Webhook replay attack | medium | mitigate | Idempotency check via processedEvents Set prevents processing same event.id twice; Stripe webhooks naturally idempotent (event.id is unique) |
| T-09-14 | Information Disclosure | Webhook response leaks tenant data | low | mitigate | Webhook controller returns only { received: true, status: string }; no tenant details in response; errors logged server-side |
| T-09-15 | Elevation of Privilege | Quota bypass via direct DB write | high | accept (plan 3 only) | QuotaGuard not implemented in plan 3; documented as TODO. Mitigation: Plan 3 focuses on tracking + billing foundation; quota enforcement deferred to follow-up or plan 4 |

## Plan 3 Known Gaps (Accepted)

- **No QuotaGuard enforcement**: Messages can be sent even if quota exceeded. Test case created but commented out. Mitigation: Implement QuotaGuard in follow-up (or plan 4 if scope allows).
- **In-memory idempotency Set**: processedEvents is process-local, lost on restart. Mitigation: Move to Redis in production (documented as TODO in code).
- **No email service**: handlePaymentFailed logs TODO instead of sending email. Mitigation: Integrate EmailService in follow-up.
</threat_model>
