# Phase 05 Plan 02: Memory Expansion (Summarization + LLM Context + REST API) Summary

Long-term memory expansion: conversation_summaries entity + BullMQ summarization job + buildLLMContext (sliding window + summary) + MemoryController REST endpoints for n8n

## What Was Built

A **Wave 2 expansion** of the Plan 01 tracer: conversation summaries generated by a background BullMQ job, LLM-context assembly combining a sliding window with older-message summaries, and REST endpoints exposing history and context to external n8n workflows. Implements MEM-03 (automatic summarization) and MEM-04 (LLM context = recent + summary).

### Task 1: Conversation Summaries + Summarization Job (MEM-03)

**ConversationSummary entity** with fields:
- `userId`, `conversationId`: Composite unique key (no duplicate summaries)
- `text`: Summary content (LLM-generated or extractive fallback)
- `messageCount`: Count of messages summarized
- `oldestMessageDate`, `newestMessageDate`: Date range of summarized messages
- `updatedAt`: Last update timestamp

**AddConversationSummaries1786500000000 migration**:
- Creates `conversation_summaries` table with dialect-aware uuid default (postgres: gen_random_uuid(), sqlite: TypeORM-generated)
- Adds unique index `UQ_conversation_summaries_user_conversation` on (userId, conversationId) (T-05-07)

**MemorySummarizationService.summarize**:
- Fetches messages for userId, skips newest 20 (sliding window)
- Returns `{ skipped: true }` when fewer than 10 older messages
- Generates summary via extractive fallback (concatenate + truncate to ~500 chars) when no LLM configured
- Upserts one row with `conflictPaths: ['userId', 'conversationId']` (T-05-07: no duplicates)
- Idempotent: second run updates existing row

**SummarizationProcessor** (BullMQ worker):
- Registered on `QUEUE_NAMES.SUMMARIZATION = 'summarization-queue'`
- Jobs enqueued with `jobId = userId:conversationId` for deduplication (T-05-06)
- Delegates to MemorySummarizationService

**Unit tests** (5 passing):
- Skips when <10 older messages
- Produces+upserts summary for >=10 messages
- Re-run updates same row (no duplicate)
- Extractive fallback produces non-empty text when no LLM

### Task 2: buildLLMContext (Sliding Window + Summary) (MEM-04)

**ConversationContextDto interface**:
```typescript
{
  summary: string | null;
  recentMessages: Array<{ role: 'user' | 'assistant'; content: string; timestamp: Date }>;
  totalMessages: number;
}
```

**ConversationMemoryService.buildLLMContext(userId, windowSize=20)**:
- Fetches recent messages via existing `getRecentMessages`
- Counts total messages for userId
- Maps messages to LLM role format: `MessageDirection.INCOMING → 'user'`, `OUTGOING → 'assistant'`
- Returns `summary: null` when `totalMessages <= windowSize`
- Returns stored summary text when `totalMessages > windowSize` and summary exists
- Returns placeholder `[N older messages not yet summarized]` when `totalMessages > windowSize` but no summary row
- Queries most recent summary by `updatedAt DESC`
- Redis cache optional (RESEARCH: degrades to direct DB query)

**MemoryModule updated**:
- Registers `ConversationSummary` entity in `forFeature([Message, ConversationSummary], 'data')`
- Exports both `ConversationMemoryService` and `MemorySummarizationService`

**Unit tests extended** (13 passing total: 7 getRecentMessages + 6 buildLLMContext):
- Returns correct shape with role mapping
- Null summary under window
- Stored summary above window when exists
- Placeholder when total > window but no summary
- INCOMING → 'user' role
- OUTGOING → 'assistant' role

### Task 3: MemoryController REST Endpoints

**GetConversationHistoryDto**:
- `take`: optional int, min 1, max 100, default 50 (T-05-05)
- `skip`: optional int, min 0, default 0 (T-05-05)
- Uses class-validator for validation

**MemoryController** routes (both require `@RequireRole(ApiKeyRole.OPERATOR)` — T-05-04):

**GET `/memory/users/:userId/history`**:
- Returns `{ messages: Message[], total: number }`
- Delegates to `ConversationMemoryService.getUserHistory(userId, { skip, take })`
- Controller clamps `take` to max 100 (T-05-05)
- Scoped by userId path param (T-05-04: no cross-user leakage)

**GET `/memory/users/:userId/context`**:
- Returns `ConversationContextDto` (summary, recentMessages, totalMessages)
- Delegates to `ConversationMemoryService.buildLLMContext(userId)`
- Scoped by userId path param (T-05-04)

**ConversationMemoryService.getUserHistory** (new method):
- Uses `findAndCount` for single query returning both rows and total
- Ordered by `createdAt DESC` (newest first)
- Empty userId returns `{ messages: [], total: 0 }`
- Soft-deleted rows auto-excluded via @DeleteDateColumn

**MemoryModule updated**:
- Registers `MemoryController` in `controllers` array

**Unit tests** (7 passing):
- Returns paginated messages scoped by userId
- Clamps take to max 100
- Uses defaults (take=50, skip=0)
- Only returns userId-scoped rows (no cross-user leakage)
- Returns buildLLMContext payload
- Returns null summary under window

## Threat Mitigations Applied

All four STRIDE threats from the plan's threat_model were mitigated:

| Threat ID | Mitigation | Implementation |
|-----------|-----------|----------------|
| T-05-04 | Scope endpoints on userId path param | Both history and context routes take `:userId` in path, service queries WHERE userId = param |
| T-05-05 | Validate and clamp pagination params | GetConversationHistoryDto: @Min(0) skip, @Max(100) take; controller clamps take to 100 |
| T-05-06 | Dedup summarization jobs | BullMQ jobId = `${userId}:${conversationId}` prevents duplicate pending jobs |
| T-05-07 | Unique constraint on upsert | Migration creates unique index on (userId, conversationId); upsert uses conflictPaths |

No additional threats discovered during implementation.

## Known Stubs

**None** — extractive fallback is functional (not a stub). Future enhancement to call external LLM via n8n is tracked in Plan 03 (retention + scheduled summarization trigger), not a stub blocking this plan's goals.
